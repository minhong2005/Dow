# Dow 运行问题与架构评审（2026-11-27）

用户期望给军师一张任务单，中途可以离开。军师应能定位输入、查看真实进度、收回成果并验收。最近一次图片生产任务暴露了这条链路的几个断点。

## 任务怎样流转

军师在独立工作区提交任务号、Markdown 任务单和附件。派单服务为普通任务创建 Codex 线程，记录线程和执行轮次，执行目录与军师目录分开。执行端写产物与回执，军师调用 collect 将结果取回。旧线程可单独配对。协议实现见 [task-pool.py](../review-runtime/handoff/task-pool.py)、[service.py](../review-runtime/handoff/service.py) 和 [pool-client.py](../review-runtime/handoff/pool-client.py)。

## 已发生的问题

| 场景 | 实际证据与用户影响 | 已做的修正 | 剩余问题 |
| --- | --- | --- | --- |
| 六个图片任务并发 | Docker 标记执行容器 OOMKilled，退出码 137。恢复后六个轮次都是 interrupted，军师此前持续看到 running。虚拟机当时约有 3.8 GiB 可用总内存，无法归因到某一单。 | 重启执行端，核对原轮次，查询时结合通道心跳。 | 多个任务共用执行服务。缺少按可用内存动态排队、按任务隔离故障和中断续作的完整流程。 |
| 通道在线，任务无进展 | 一单因缺 Pillow 请求在沙箱外探测 PyPI，线程等待批准。后台服务没有将具体请求送到可交互的窗口，军师以为还在裁图。 | 查询显示 waiting_on_approval。新后台池设 approvalPolicy=never，原网络与工作区限制继续生效。本地单独提供 Pillow，并用真实照片验证解码、裁切和保存。 | 手工提供的 Pillow 尚未纳入公开镜像构建。无依赖预检，缺字体、编解码器或其他工具时仍可能在任务中途失败。running 也没有逐张进度。 |
| 工作完成但回收失败 | 一个图片工作目录约 15 MiB，超过单次交接的 12 MiB 上限。军师拿不到图库，改走 Mac 命令又遇到确认。最终从源目录复制到军师目录并逐文件校验。 | 保住了当次产物。现有协议对文件类型、数量和总大小有检查。 | collect 会打包工作目录，输入和输出可能一起计入。缺少输出清单、分块传输、中断续传。批准框未出现的原因尚未验证。 |
| Windows 一会儿在线一会儿离线 | 工作机仍尝试 Mac 的旧局域网地址。实测心跳约 10.8 秒，超过 8 秒租约。一次截图成功不能证明下次点击能执行。 | 修正地址、重连后连续 10 次截图成功。发出 3 次测试点击，独立测试窗口实际收到 3 次。 | 地址再次变化仍可能复发。应分别观察主机在线、共享租约有效、请求已领取、界面操作已执行及回执已送达。 |
| 复制会话后用户以为原聊天消失 | 创建副本会把当前视图切到新会话。查目录和容器后确认原会话仍在运行。 | 可以从列表重新进入原会话。 | 应清楚标记副本来源，区分项目文件复制、CLI 历史和眼下显示的终端。 |

## 希望评审者回答

1. 任务状态应由哪些事件驱动？执行端消失、等待批准、工具执行中、产物已写但未收回，应如何呈现和恢复，才能避免重复执行同一单？
2. 怎样让军师自由提交任务，同时在执行端按内存与磁盘压力排队？哪个组件应决定暂停、恢复和重试？
3. 能否按任务类型声明依赖，在提交时验证离线环境？如何保证今天补上的依赖在下一次重建容器后仍然可用？
4. 图片和 ZIP 是否应经独立的产物通道传递？如何校验清单、哈希、大小和访问范围，让收件端能断点续传？
5. Windows 更换地址、任务执行时用户接手桌面、操作成功但回执丢失，这三种情况该如何测试？哪些操作可重试，哪些重试可能重复点击或重复提交？

## 建议的端到端验收

从空白安装环境提交一单实际图片任务，提供输入、生成输出、回收并验收。再注入三次故障：执行进程退出、结果超过 12 MiB、Windows 地址变化。记录军师看见的状态、最后持久化的进度、人工介入次数，以及恢复后是否重复执行。上述整套故障验收尚未跑通。

网络验收应分别记录终端与浏览器的实测出口，以及中转断开后是否仍能直连。出口验证无法推断第三方平台的账号判定原因。
